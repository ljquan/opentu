# AI 任务队列多结果插入画布修复人工测试文档

**日期**：2026-08-21

**测试对象**：包含本修复的 `develop` 派生分支

**局域网地址模板**：`http://${LAN_HOST}:${PORT}/`

**关联 Docs**：[AI 任务队列多结果插入画布修复交接文档](../docs/2026-08-21-AI任务队列多结果插入画布修复-交接文档.md)

## 验收目标

1. 单个完成任务含多个结果 URL 时，用户点击一次“插入”即可插入全部结果。
2. 不再出现 `Cannot read properties of undefined (reading 'clientWidth')`。
3. 修复按结果数量和媒体类型生效，不依赖 MJ 分组或模型名称。
4. 真正单 URL 图片、拖拽和普通单项插入行为保持不变。
5. 暂存过程中任一后续结果失败或画板切换时，不向真实画板写入半成品。

## 范围边界

- “单任务多结果”指一个任务的 `result.urls` 含多个 URL，不是用户多选多个任务。
- 本文验证任务结果插入，不验证 MJ/GPT Image/Gemini 的生成质量、计费或供应商路由。
- 图片为主验收对象；视频和 SVG 用于验证共用暂存机制。
- HTTP `200` 只表示服务可达，最终通过必须检查真实画布节点和媒体可见性。

## 前置条件

1. 从测试分支启动服务并监听 `0.0.0.0`。
2. 准备一个已完成的 MJ 图片任务，且同一任务有 4 个有效结果 URL。
3. 准备一个真正只有 1 个结果 URL 的图片任务。
4. 准备至少一种非 MJ 多 URL 图片任务，例如 GPT Image、Gemini 或自定义 HTTP 供应商。
5. 若入口可用，准备双视频、双 SVG 或等价的测试数据。
6. 使用空白测试画板并记录测试前元素数量；打开浏览器控制台。
7. 测试记录不得包含 API Key、Cookie、完整鉴权头或未脱敏用户数据。

## 人工测试场景

### 场景 1：MJ 单任务 4 个结果

1. 打开任务队列，找到缩略图标记“4 张”的已完成 MJ 任务。
2. 记录画布元素数量。
3. 只点击一次该任务右侧“插入”。
4. 检查画布、任务状态、提示消息和控制台。

**预期结果**：

- [ ] 一次点击新增 4 个图片元素，不要求用户进入多选模式。
- [ ] 四张图片按任务结果顺序排列，尺寸与间距稳定，不叠加。
- [ ] 所有图片可见，画布缩放、选择和拖动仍可用。
- [ ] 不出现 `clientWidth`、空白节点或未处理异常。
- [ ] 成功消息只出现一次，任务正确标记为已插入。

### 场景 2：真正单 URL 图片回归

1. 找到只有一个结果 URL 的已完成图片任务。
2. 点击一次“插入”。
3. 检查元素数量、选中与布局行为。

**预期结果**：

- [ ] 只新增一张图片，不重复插入。
- [ ] 普通单项 Plait 插入、选择和滚动行为与修复前一致。
- [ ] 不进入多结果暂存路径，不出现控制台异常。

### 场景 3：非 MJ 单任务多结果

1. 选择 GPT Image、Gemini 或自定义 HTTP 供应商产生的多结果任务。
2. 点击一次“插入”。

**预期结果**：

- [ ] 全部结果一次插入，顺序、尺寸和布局正确。
- [ ] 行为与 MJ 一致，没有模型名或分组特判。
- [ ] 不出现 `clientWidth` 异常。

### 场景 4：后续结果失败的原子性

1. 准备一个至少含两个结果的任务，使第二个 URL 无法加载或缓存缺失。
2. 记录测试前画布元素数量并点击一次“插入”。

**预期结果**：

- [ ] 返回明确的资源加载或缓存错误。
- [ ] 真实画布元素数量不变，不残留第一个结果的半成品。
- [ ] 任务不误标为已插入，错误提示不重复。
- [ ] 修复资源后可再次插入成功。

### 场景 5：视频与 SVG 共用暂存路径

1. 分别触发双视频和双 SVG 的一次性插入入口。
2. 检查节点、媒体展示、URL 与交互。

**预期结果**：

- [ ] 所有结果按顺序插入，不出现 DOM 宿主异常。
- [ ] 视频可播放，SVG 可见，尺寸与元数据正确。
- [ ] 失败时遵守与图片相同的半成品保护。

### 场景 6：混合媒体

在支持混合 item 的入口中一次插入图片、视频、SVG、文本或音频组合。

**预期结果**：

- [ ] 项目顺序与布局稳定，各媒体节点类型正确。
- [ ] 每项只绑定自己的生成元数据，不串任务。
- [ ] 图片类暂存不依赖临时画板 DOM，其他媒体原逻辑不退化。

### 场景 7：暂存期间切换画板

1. 使用加载较慢的多结果任务开始插入。
2. 在准备完成前切换到另一个画板。

**预期结果**：

- [ ] 插入被取消并给出明确提示。
- [ ] 原画板和新画板都不出现迟到节点或半成品。
- [ ] 返回原画板后可以重新发起插入。

### 场景 8：连续插入与性能

1. 连续插入两个不同的 4 结果任务。
2. 如数据允许，再验证 10 和 20 个结果。
3. 观察交互响应、内存和任务元数据。

**预期结果**：

- [ ] 每次点击只提交一次，节点不重复，两个任务元数据不串线。
- [ ] 页面无明显长时间冻结，完成后内存不持续增长。
- [ ] 不出现大量 Blob 并发读取或持续增加的临时 DOM/对象引用。

### 场景 9：局域网 HTTP

1. 从同一局域网设备打开 `http://${LAN_HOST}:${PORT}/`。
2. 重复场景 1、2 和 4。
3. 检查真实媒体可见性、控制台和网络响应。

**预期结果**：

- [ ] 工作台和任务队列可正常使用，不只是首页返回 `200`。
- [ ] 真实图片可见；缓存或 Service Worker 不可用时有明确错误。
- [ ] 多结果插入不出现 `clientWidth` 或 SPA HTML 冒充媒体。

## 通过标准

1. MJ 单任务 4 结果一次点击全部插入，且不出现 `clientWidth` 异常。
2. 至少一种非 MJ 多结果任务表现一致，证明修复不依赖供应商特判。
3. 单 URL 图片保持原行为；视频、SVG 和混合媒体无回归。
4. 后续 item 失败或切换画板时，真实画板不残留半成品。
5. LAN 环境必须验证真实画布和媒体可见性，不能只以 HTTP `200` 判定通过。
