## 验收目标

1. 可信 Tuzi 同步图片正式 `POST` 前已持久化提交身份，请求只提交一次；
2. 页面刷新或可恢复的网络结果未知后，原任务使用同一 Request ID 只读找回结果；
3. 明确失败、取消、异步协议和缺少元数据的旧任务不误入恢复；
4. 取消、删除、重试和同 ID replacement 后，旧请求、轮询和回调不能改写新实例；
5. 响应体、轮询、缓存和 Custom HTTP multipart 文件读取受超时、取消、数量和字节上限约束；
6. 既有图片、文本、音频和视频执行语义不回归。

## 范围边界

- 本次验收不评估图片美术质量、模型效果或上游生成速度。
- 不要通过主动重发 `POST` “帮助恢复”，否则无法验证只读恢复。
- 不要把局域网页面 HTTP 200 或生成面板可见当作恢复成功。
- 不验收旧任务猜测迁移、24 小时补偿、任意地址代理或第三方恢复；这些均不在设计范围内。
- 真实上游故障注入可产生计费，只在受控测试账号和额度下执行。

## 前置条件

1. 准备可查看 Network 日志的 Chromium 浏览器，开启“保留日志”；
2. 准备可信 Tuzi 同步图片模型和脱敏测试配置；
3. 至少覆盖一个固定同源代理节点和一个 Request-ID-CORS 兼容节点；
4. 准备可控的 fetch/响应体中断、慢响应、404/5xx 和结果查询响应注入方式；
5. 竞态和字节上限项优先使用自动化或本地可控服务，不向真实上游上传大文件；
6. 任何截图、HAR 或报告不得记录完整 API Key、Cookie、Token、签名 URL 或原始图片数据。

## P0 核心验收

### 场景 1：正常提交与部署路由

1. 分别在本机、局域网和公网测试环境提交一次同步图片生成；
2. 覆盖普通可信节点和 Request-ID-CORS 兼容节点；
3. 记录正式 `POST`、Request ID 和后续请求。

**预期结果**：

- [ ] 正式 `POST` 前任务已保存 `submissionRequestId`、已提交标记和实际调用路由；
- [ ] 请求只有一个 `X-Request-Id`，首次提交时与任务 ID 一致；
- [ ] 普通节点经固定同源代理保持原节点、Token 和计费域，兼容节点保持直连；
- [ ] 健康请求期间没有 `/images/generations/result` 查询；
- [ ] 每个用户操作只产生一个图片 `POST`。

### 场景 2：网络 fetch 结果未知

1. 在可信同步图片 `POST` 已发出后中断 fetch；
2. 保持页面不刷新，观察任务状态和 Network；
3. 让结果查询依次返回 `processing_or_not_found` 和成功结果。

**预期结果**：

- [ ] 当前尝试先持久化为 `PROCESSING + POLLING`，再释放执行锁；
- [ ] 执行锁释放后才发起只读结果 GET；
- [ ] GET 使用原 `submissionRequestId`，且不携带 `X-Request-Id`；
- [ ] 不会发送第二个图片 `POST`；
- [ ] `processing_or_not_found` 结束当轮，有界退避后继续；
- [ ] 成功结果回到原任务、原卡片和批量预览。

### 场景 3：成功响应体读取中断

1. 让同步图片 `POST` 先返回 2xx Header；
2. 在响应体完整读取前中断流；
3. 分别验证流抛错、流忽略 Abort 且不结束两种情况。

**预期结果**：

- [ ] 可信同步图片成功响应体中断进入同 Request ID 只读恢复；
- [ ] 忽略 Abort 的流仍会被原硬超时或用户取消使 Promise 结束；
- [ ] reader、超时定时器和取消监听被释放；
- [ ] 没有第二个图片 `POST`。

### 场景 4：刷新后自动恢复

1. 确认正式图片 `POST` 已发出；
2. 在返回结果前刷新页面；
3. 不打开图片生成面板，等待恢复结果。

**预期结果**：

- [ ] 启动扫描只恢复元数据完整的同步图片任务；
- [ ] 延迟运行时自动唤醒，无需用户打开生成面板；
- [ ] 页面仅发送使用刷新前 Request ID 的结果 GET，不重发图片 `POST`；
- [ ] 恢复成功后原任务完成，原卡片显示结果；
- [ ] 缓存写入失败时保留已验证远程 URL，任务仍能完成。

### 场景 5：取消、删除、重试和同 ID replacement

1. 让旧任务分别停在执行队列、正式请求、恢复轮询、结果下载和终态写回；
2. 在各阶段执行取消、删除或重试；
3. 通过备份导入、GitHub 同步或显式删除后恢复安装同 ID 新对象；
4. 让旧回调和旧 `finally` 在新对象安装后迟到。
5. 分别对终态任务和活跃 CHAT/VIDEO 任务注入 IndexedDB 删除失败。

**预期结果**：

- [ ] 已取消的等待项不发起 provider 请求；
- [ ] 重试保持本地任务 ID，但生成新 `submissionRequestId`；
- [ ] replacement 更新生命周期令牌并且只执行新参数；
- [ ] 安装 replacement 前已停止旧图片恢复和旧执行；
- [ ] 旧进度、remote ID、缓存结果、错误和终态不能覆盖新对象；
- [ ] 旧清理不能释放新对象的执行或轮询槽位；
- [ ] 删除 tombstone 保留到串行化写入排空，全部清空后旧写入不会复活任务。
- [ ] 持久化删除失败时，终态任务回退到原终态，活跃 CHAT/VIDEO 任务回退为“已取消”，不成为无主的“处理中”任务。

## P1 异常与安全验收

### 场景 6：不可恢复错误与协议排除

分别触发明确 HTTP/业务错误、正常关闭但结构非法的 JSON、用户取消、`/videos`、Google `generateContent`、带 `pollPathTemplate` 的自定义 binding 和非 `POST` 图片请求。

**预期结果**：

- [ ] 各路径保留原错误、取消或异步轮询语义；
- [ ] 不进入固定同步图片结果查询；
- [ ] 不误写 `PROCESSING + POLLING`，不多发图片 `POST`。

### 场景 7：恢复元数据、设置初始化与截止时间

1. 分别恢复缺少 `submissionRequestId`、已提交标记、`SUBMITTING/POLLING` 阶段或可信实际路由的任务；
2. 让 provider 设置解密持续 pending 到原截止时间；
3. 让设置初始化 reject，或让原 profile/model/binding 无法解析；
4. 在候选等待时恢复其他无关任务。

**预期结果**：

- [ ] 缺少元数据的旧任务不猜测 Request ID、不查询、不重提；
- [ ] 只有图片恢复候选等待设置解密，其他任务正常恢复；
- [ ] 等待保留原 `startedAt`，不重置或延长 15 分钟截止时间；
- [ ] pending 超时写入 `RECOVERY_TIMEOUT`；reject 或路由缺失写入 `RECOVERY_ROUTE_UNAVAILABLE`；
- [ ] 迟到的设置初始化结果不能复活终态或 replacement。

### 场景 8：结果响应校验与缓存降级

使结果端点分别返回 `processing_or_not_found`、成功、明确失败、401/403、Request ID 不匹配、带凭据 URL、非 HTTP(S) URL、超限响应体和可用结果但缓存失败。

**预期结果**：

- [ ] 处理中结果只等待下一轮，不在同轮遍历所有节点；
- [ ] 明确失败写入脱敏上游错误；
- [ ] 401/403 立即写入凭据失效，不继续扫描其他节点；
- [ ] Request ID 不匹配或为空的终态响应被忽略，不触发成功或失败回调；
- [ ] 无效 URL 和超 256 KiB 恢复响应被拒绝；
- [ ] 缓存失败不丢弃已验证远程 URL；
- [ ] 已观测的成功或失败优先于同时到达的截止时间。

### 场景 9：响应体硬超时与字节上限

1. 对显式使用受控非流式 reader 的 provider，分别返回大于 64 MiB 的成功体和大于 1 MiB 的错误体；
2. 分别通过 `Content-Length` 声明超限和实际流字节超限；
3. 让 2xx 和错误响应的流忽略 Abort 且不关闭；
4. 对使用原生 reader 的请求只返回 Header。

**预期结果**：

- [ ] 声明或实际超限均立即拒绝并取消当前 reader；
- [ ] 原硬超时和用户取消可使忽略 Abort 的流结束；
- [ ] 错误响应保留超时、取消、字节上限或流错误语义，不进入图片恢复；
- [ ] 未声明受控 reader 的请求在 Header 返回后立即释放未使用的 transport 超时和监听。

### 场景 10：Custom HTTP multipart 输入安全与资源上限

分别测试有效 data URL、同源 HTTP(S)/blob URL、无凭据公网 HTTP(S)，以及嵌入凭据 URL、localhost/私网/链路本地跨源目标、重定向、非图片 MIME、超 20 MiB 单文件、超 16 文件、超 64 MiB 文件总量、超 1 MiB 文本和下载期间取消。

**预期结果**：

- [ ] 合法来源按顺序读取，且每个文件使用剩余总预算；
- [ ] 跨源请求使用 `credentials=omit`、`referrerPolicy=no-referrer`、`redirect=error`；
- [ ] 非法来源、MIME、声明长度或实际流超限在 provider `POST` 前失败；
- [ ] 流式初始缓冲不超过 64 KiB，不同时将多个大文件完整保留在内存；
- [ ] 取消会停止当前 reader，不再发送 provider `POST`。

### 场景 11：凭据、GET 和 fallback 边界

1. 对恢复 GET 和其他 GET/HEAD 传入不同大小写的 `X-Request-Id`；
2. 使用第三方绝对 URL 和自定义 provider；
3. 让携带有效 Request ID 的图片 `POST` 返回 404/5xx 或网络中断；
4. 让未携带有效 Request ID 的旧图片端点返回明确 404。

**预期结果**：

- [ ] GET/HEAD 不携带任务 Request ID，残留 Header 被清理；
- [ ] 第三方目标不接收 Tuzi Token、查询凭据或任务 Request ID；
- [ ] 携带有效 Request ID 的图片 `POST` 不因网络错误、404 或 5xx 跨节点重发；
- [ ] 仅未携带有效 Request ID 且收到明确 404 的图片端点沿用可信 fallback；
- [ ] 被替换的 fallback Response 体被释放。

### 场景 12：其他媒体和执行回归

分别执行普通图片、异步图片、文本、音频和视频任务，并在执行中做取消、重试和同 ID replacement。

**预期结果**：

- [ ] 正常图片继续完成原缓存、卡片和批量预览流程；
- [ ] 异步图片和视频保留各自的 remote ID/轮询语义，不进入同步图片恢复；
- [ ] 文本、音频和视频的迟到结果不能覆盖同 ID 新实例；
- [ ] 失效的视频轮询停止发请求，持久化路由缺失时明确失败；
- [ ] 取消、删除、重试和卸载后无残留定时器、队列项、AbortController 或长期占用的大响应引用。

## 通过标准

1. P0 场景在目标部署环境全部通过；
