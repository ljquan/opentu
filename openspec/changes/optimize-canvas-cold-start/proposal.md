# Change: 优化首次进入可操作画布的加载链路

## Why

用户反馈首次打开工作台加载缓慢。当前 `develop@794a3fc0` 已包含入口拆包修复，但启动预算只覆盖 HTML → main → bootstrap 的静态依赖，没有覆盖随后立即加载的 Drawnix 画布。仅缩短启动遮罩显示时间，不能证明用户更早获得可操作画布。

只读检查发现画布仍通过工具插件、图片组件、任务提醒及测试助手静态引用任务执行器、生图适配器和工具服务。应以实际构建和冷启动结果确定分批拆分范围。

## What Changes

- 扩大启动分析和构建检查，分别统计启动壳层与画布必需资源的依赖闭包、总下载体积和最大分块。
- 对构建结果确认的可选重依赖按调用场景加载，优先处理图片组件的生图操作、工具生成处理、工具测试助手和任务执行器加载边界。
- 保留已有画布渲染、保存、撤销及任务恢复语义；确有待恢复任务或用户触发功能时，可靠地唤醒所需运行时。
- 补充启动阶段与真实画布就绪的观测，验收以画布挂载和可交互为准。
- 同一版本、同一网络条件下对比生产构建的首次启动，覆盖已有画布和需要恢复任务的场景。

## Scope And Approval

用户已选择方案 B，批准继续拆分实际画布的可选依赖并进行验证。

推荐分批优化实际画布依赖；另一个选择是仅核对并部署已有 1.2.18 启动修复。两者的成本、风险和适用场景见 `design.md`。部署、提交和 PR 不包含在本提案的默认执行范围。

## Impact

- Affected specs: `startup-performance`；衔接 `refactor-startup-shell-loading`，不重复改造既有离线升级协议。
- Affected code: `apps/web/src/app`、`packages/drawnix/src` 的画布可选功能依赖边界、`scripts/validate-startup-bundle.js` 及相关回归测试。
- 不新增持久化字段、数据库结构、配置项或依赖版本；如实际实现需要新增字段，必须补齐所有调用方、默认值和旧数据兼容后再提交 PR。
