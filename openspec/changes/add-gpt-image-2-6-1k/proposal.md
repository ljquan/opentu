# Change: 接入 Tuzi gpt-image-2.6-1k

## Why

用户要求在最新 develop 的 OpenTu 中接入 `gpt-image-2.6-1k`，参考聊天“添加 gpt-image-2.6-1k 描述”（01a1a9fb-435e-79f3-819b-741af4a88036）。该聊天中用户已说明只有 `-1k` 上线，GIF 通过提示词“生成 GIF 图”请求；渠道文案说明图片保留实际返回尺寸，不能把 1k 当作固定 1024×1024。

当前目录没有此型号。`isGPTImage2ModelId` 会把 2.6 识别成 2；若只追加模型条目而不维护 GPT 参数分组，新型号还会进入 Gemini 参数列表。底层已有 GIF/SVG MIME 识别，但尚未完成该型号的实际请求、缓存、预览和下载验证。

## What Changes

- 注册精确型号、显示名称、简码和渠道能力说明，补齐所有必填元数据；不增加未上线的 2.6 其他后缀。
- 独立定义 2.6-1k 的型号判断和参数能力，修复与 GPT Image 2、Gemini 的误分类；不直接复制 2.5 的固定尺寸集合、画质或高分辨率参数。
- 复用现有按供应商配置选择的图片适配器，保持请求模型 ID 和供应商绑定一致；不自动改写为 2.5，也不切换用户凭证。
- 默认采用自动尺寸；仅开放经渠道合同或实测确认的参数，清理切换模型时遗留的不兼容参数。按返回媒体实际尺寸入画布。
- 尺寸复测后开放自动、1:1、2:3、3:2、16:9、9:16；生成与编辑路径保留已验证的尺寸值，不再将显式选择统一覆盖为 auto。方形/GIF 等输出可能使用渠道自身像素尺寸，因此界面按比例展示，不承诺固定像素。
- 验证静态图片、提示词生成 GIF、SVG 的实际响应形式，完善必要的解析、缓存、预览及原文件下载处理，保留 MIME、扩展名和 GIF 动画帧。
- 增加型号分类、参数切换、请求路由、返回格式及旧型号回归测试，并记录真实接口与浏览器验证结果。SVG 作为图片资源展示，不直接插入不可信 SVG DOM。
- 不引入新持久化字段；若实现确需新增字段，先补齐默认值、序列化、读取兼容和迁移验证。

## Options

| 方案 | 优势和适用场景 | 缺点、维护成本和风险 |
|---|---|---|
| 最小配置接入 | 变更少，适合先提供静态生图入口 | 仍需修复分类；GIF/SVG 未形成验收闭环，后续可能补修 |
| 完整接入与格式回归（推荐） | 覆盖用户引用的图片、GIF、SVG 能力及保存下载链路 | 测试范围较大；渠道不支持或返回协议不明确的能力需明确标注，不能宣称通过 |

## Impact

- Affected specs: `image-generation`, `runtime-model-discovery`。
- Affected code: `packages/drawnix/src/constants/model-config.ts`、图片参数解析器、GPT/Tuzi 图片适配器及其路由测试；根据验证结果调整 `packages/utils/src/url`、媒体缓存、画布展示和下载链路。
- 与已有 `update-default-model-catalog`、`update-image-api-compatibility-modes`、`add-gpt-image-profile-compatibility` 共享代码；以当前 develop 的实现为基准，不重做路由体系。
- 不变更默认模型、既有型号尺寸规则、数据库或计费配置。

## Approval and Validation

用户于 2026-11-05 明确批准“完整接入（推荐）”。客户端实现及验证已完成，详细结果见 `validation.md`。真实 SVG 生成被上游以 HTTP 400 拒绝，目前只确认有效 SVG 返回值的客户端处理可用，不宣称渠道 SVG 生成功能已经可用。验收区分模拟测试与真实接口测试，不把单次成功等同于上游永久可用。

## 2026-11-08 后续适配

用户继续要求适配已上线的 `gpt-image-2.6-flare`、`gpt-image-2.6-sunburst`，并提供渠道完整 GIF/SVG 请求说明。原范围中“仅增加 -1k”的限制由本次明确需求更新：补齐两个精确型号和输出类型入口，按提示词 GIF、官方参数 GIF、官方 SVG 分别构造请求。分组由令牌决定，界面不切换分组；未得到新型号实测授权，不执行收费调用。`-1k` 保留原有提示词协议。最终实现、适配限制和验证结果见 `validation.md` 的本日最终状态。

用户随后提供无后缀 `gpt-image-2.6` 的模型截图并要求适配。将该精确 ID 纳入既有 2.6 图片模型与请求参数规则，补齐名称、简码和图片说明；修正自动发现和历史目录中的文本误分类，保留显式手动配置。复用现有尺寸、输出格式、编辑及路由链路，不改写为 Flare 或 Sunburst，不新增收费调用。客户端协议复用以本地测试验证，渠道实际可用性和帧数上限不从其他型号推断。

用户进一步要求补齐 2.6 的透明图、输出格式等参数。对无后缀、Flare、Sunburst 的静态输出接通已有图片兼容字段：background、PNG/JPEG/WebP、output_compression、quality、moderation、user，以及参考图编辑的 input_fidelity。字段贯通共享界面、队列、GPT/Tuzi JSON 和 multipart、基础兼容路径；GIF/SVG 隔离静态字段，透明背景与 JPEG 冲突在发送前报错。`-1k` 为文档明确的按次路由别名，保持此前契约。此范围为现有非流式图片链路的参数适配，不承诺所有渠道均接受每个字段、不将通用文档当作 2.6 型号的完整能力表，也不包含新的收费实测。

用户随后反馈实测：default 分组的 Key 也可使用官方参数方式，SVG 不可用。对应修正 GIF 分组说明，将界面“GIF（官方参数）”改为“GIF（参数）”，帧数标签去除“官方”；保留 SVG 的官方/官方优惠分组说明。沿用已保存的 gif_official 参数值及现有请求，不将用户反馈扩展为所有字段、型号、Codex 分组或任意帧数均已验证。

用户进一步明确“2.6 都覆盖”，具体指透明背景等静态参数。将静态参数范围扩展到全部四个已注册的精确 2.6 型号，包括 `-1k`：共享背景、PNG/JPEG/WebP、压缩、质量、参考图保真度和已有高级字段。此前对 `-1k` 不开放静态字段的范围由此最新要求更新，保留该别名的 b64_json 返回格式和原有 GIF/SVG 模式限制；不增加真实收费调用，也不宣称各渠道的透明 Alpha 已实测。

用户随后截图反馈在“GIF（参数）”模式仍看不到透明参数。原因是上一阶段将背景和画质与静态编码一起限定为 auto 模式。现修正为两种 GIF 模式都显示并传递背景、画质和已有通用图片字段；PNG/JPEG/WebP、静态压缩和编辑保真度继续只用于 auto，SVG 保留专用参数。GIF 透明请求不自动指定 PNG，历史静态编码也不覆盖 GIF 格式；不新增收费实测或承诺渠道已输出透明 GIF。

用户进一步反馈 default 分组一次任务可能返回 GIF 与原图，要求整理多图生成的画布位置，并明确选择“按任务分列：GIF 在上、原图在下”。本轮按该效果修正 2.6 多结果排版，保留全部输出和原始结果/缓存顺序；新普通非 SVG 2.6 请求预留整列，多个任务横排，插入时逐图读取尺寸并整组避让。覆盖自动、重试及现有手动插入入口，不重排已有画布内容，不增加生成请求。最终验证及限制见 validation.md 的多结果排版记录。
