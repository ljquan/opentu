## Context

当前外部脚本通过 Playwright 操作线上 OpenTu iframe。该方式虽然能创建真实任务，但必须启动独立浏览器配置，无法接管用户普通 Chrome 中已经打开的 OpenTu。浏览器安全模型也不允许一个普通 Node.js 进程无调试端口地接管现有 Chrome。

仓库已有模型评测工作台、运行时模型目录、统一任务队列与图片生成适配器，因此巡检应成为 OpenTu 内部能力，而不是继续加强外部浏览器自动化。

## Goals / Non-Goals

### Goals

- 巡检由 Tuzi 服务端常驻后台执行，关闭、刷新 OpenTu 或浏览器断网不会中断。
- OpenTu 在同一工具窗口触发并查看服务端真实任务、图片 URL 和完整报表。
- 遍历所有分组，但仅覆盖用户指定的 GPT Image 2 与 Gemini 模型白名单，其他模型一律跳过。
- 提供比例、尺寸/分辨率严格校验，以及用户指定格式的完整结果报表。
- 复用现有工作台和服务，限制内存占用，不读取或复制图片大二进制。

### Non-Goals

- 不再通过 Playwright、CDP 或 Apple Events 接管浏览器。
- 不启动独立 Chrome、独立用户目录或第二套 OpenTu。
- 不自动把巡检结果插入画布。
- 不依赖独立浏览器、LaunchAgent 或页面常驻来维持巡检。

## Decisions

### 1. 独立报表工具，复用现有工具窗口系统

注册独立的“生图巡检报表”内部工具，并从左侧工具栏直接打开。报表复用现有工具注册表、工具窗口服务、运行时模型目录和任务队列，不再把巡检塞进模型测试工作台，也不增加外部浏览器实体。

### 2. 巡检任务由服务端持久执行

OpenTu 通过当前 Token 创建服务端巡检运行。服务端按用例真实调用现有图片生成链路，并持久化：

- 当前分组对应的 `modelRef`
- 模型 ID
- 比例
- 分辨率/质量档位
- 唯一 `inspectionRunId`、`inspectionCaseId`
- 请求和实际尺寸、图片 URL、耗时、状态、错误与校验公式

创建接口按 Token 幂等：已有运行中任务时返回当前运行，不重复创建。每个用例在持久化后生成稳定的内部请求 ID，真实任务提交和恢复均按该 ID 对账；慢提交期间持续续租，避免其他 Worker 重复领取。服务端重启后从持久状态恢复未完成运行；单个用例失败只记录该用例并继续后续用例。真实任务默认最多等待 120 分钟，可通过 `IMAGE_INSPECTION_CASE_TIMEOUT_MINUTES` 调整；恢复时沿用用例首次 `started_at`，超时只结束巡检等待并保留任务 ID，不重新提交同一任务。运行汇总在数据库锁内重新聚合，并由 Worker 每分钟对账活动运行，避免并发终态回退或最后一次汇总失败后永久悬挂。停止运行后，当前轮询用例会在下一轮状态同步时停止续租并进入终态。

对账查询错误与“任务不存在”严格区分：存储暂时不可用时归还租约等待恢复，绝不继续提交。已经持久化稳定请求 ID 或任务 ID 的用例不受通用 3 次崩溃恢复上限影响，而由持久化的单用例超时兜底；周期对账以 200 条小批量分页扫描全部活动运行，避免高并发下后续运行长期得不到汇总。停止服务会等待后台 Worker 协作退出，防止快速重启时旧新 Worker 短暂重叠。

### 3. 动态构建测试矩阵

- 模型范围使用精确 ID 白名单：`gpt-image-2-vip`、`gpt-image-2`、`gemini-3.1-flash-image-preview`、`gemini-3-pro-image-preview`、`gemini-3-pro-image-preview-2k-vip`、`gemini-3-pro-image-preview-4k-vip`、`gemini-3.1-flash-image-preview-4k`、`gemini-3.1-flash-image-preview-2k`、`gemini-3-pro-image-preview-4k-async`。
- GPT Image 2 系列使用项目内声明的精确比例与 1K/2K/4K 尺寸矩阵。
- Gemini 白名单内的动态型号读取运行时模型能力，覆盖其声明的全部比例和 1K/2K/4K/HD 档位。
- 名称固定档位的 Gemini 白名单型号仅测试对应档位。
- 同模型在不同分组分别创建任务，保证每个分组的真实路由都被覆盖。

### 4. 服务端分页汇总，不持有图片二进制

巡检状态仅保存任务 ID、URL、宽高、耗时、错误和必要计费元数据。图片预览直接使用 URL，不将图片转成 base64，不批量下载图片；前端同一时间仅挂载一张展开的实际图片，收起或切换后立即卸载，避免多张 2K/4K 图片同时解码。运行历史与用例结果均由服务端分页，前端不一次加载整场数千条结果。

### 5. 尺寸判定

- `default` 分组的 `gpt-image-2`、`gpt-image-2-vip` 忽略像素档位，仅按宽高最大公约数精确约分后的比例判断；例如 `1086×1448 → 3:4` 通过，近似但不能精确约分的比例失败。
- 其他分组的 GPT Image 2 使用精确宽高匹配。
- 其他动态模型同时校验比例容差和分辨率长边档位。
- 若 URL 含可识别的 base-30 尺寸编码，报表展示 `parseInt(encoded, 30)` 公式；否则展示实际图片宽高和总像素计算。
- 4K 型号返回 2K 等降档结果必须判定失败。

### 6. 服务端定时与前端重连

Tuzi 服务端每日 07:00 调度，仅在中国法定工作日执行：法定节假日和普通周末跳过，调休补班日照常执行。生产环境必须显式配置固定的 `IMAGE_INSPECTION_TOKEN_ID`，未配置时跳过自动巡检，避免多用户环境误用最近一次手动运行者的 Token。调度通过数据库幂等约束避免多实例或重启重复创建。OpenTu 仅在报表打开时轮询；运行中约 2–3 秒刷新，网络异常指数退避至最长约 30 秒，页面重新可见或恢复网络时立即刷新。普通接口请求采用 45 秒截止，完整导出采用 5 分钟截止，防止半开连接永久吞掉后续轮询；关闭报表时统一取消轮询与用户动作请求，避免卸载后继续调度。停止轮询不等于停止服务端任务。

## Risks / Trade-offs

- 一次全量巡检会创建大量真实任务，可能占用后台队列较长时间。通过有界并发、停止按钮、进度显示和持久恢复控制影响。
- 部分供应商返回尺寸元数据与实际图片不一致。校验优先收集接口尺寸、自然尺寸、URL 尺寸并明确展示各来源，不以单一来源误判通过。
- 服务端部署前，旧前端版本仍不具备可靠后台能力；前后端接口必须一并上线。

## Migration Plan

1. 停用旧 LaunchAgent，避免继续打开独立 Chrome。
2. 实现并验证 Tuzi 服务端持久巡检与 OpenTu 内置报表客户端。
3. 保留旧报表文件供查看，但不再运行外部 Playwright 脚本。
4. 验证稳定后删除旧脚本的自动化浏览器配置目录与前端页面内调度代码。
