# OpenTu 对接 Tuzi 渠道分析 v2.2

本实现使用每次模型请求的 query `ch`。已由用户确认按 v2.2 实施，并已部署到指定测试平台，不调整 Key 发放、复用、账户、鉴权或计费。远程没有 dev 分支，已同步实际开发分支 origin/develop 至 `7b3aa15e`（1.2.0），PR 分支为 `codex/opentu-client-channel-v22`；从原工作区只提取渠道归因相关改动。早期部署及测试版本见历史各节，最新复核见文末。

## 渠道与注入边界

| 运行 origin | ch |
| --- | --- |
| `https://opentu.ai` | 1 |
| `https://pr.opentu.ai` | 2 |
| HTTP(S) localhost / 127.0.0.1 / IPv6 loopback | 2 |
| 其他 / native scheme | 0 |

3 为桌面正式版预留，4 为桌面测试版预留，当前均未启用。后缀相似域名不等于正式/测试 origin。ch 可伪造，仅用于业务分析，不作为身份、安全或计费依据。

2026-10-21 用户确认 Tuzi 管理页面仅可选正式网页/测试网页，桌面正式版/测试版显示为禁用预留项；不再提供“未归因”和“全部渠道”入口。底层仍保留 0 及 API 0/all 兼容行为，不改账务或原始记录。本内网测试页面依协议仍上报 0，不冒充测试域名流量。

`tuzi-client-attribution.ts` 读取渠道，仅对 `tuzi-api-endpoints.ts` 中精确受信或当前部署配置的 Tuzi API origin 注入；不使用宽泛子域匹配。已存在的所有 ch（含编码键名）先删除，再加单个当前值。其他 query 原字节、hash、正文、请求头、显式 0/false 和取消信号保留。

接入点覆盖共享 provider transport、独立文本/图片/视频/音频、模型插件及工作流本地调用。插件先序列化 params 再去重 ch。启用本地代理时先标记内层目标，再包代理，已有代理不重复嵌套；Request 对象保留正文/头/信号。签名素材下载、WebDAV 和第三方 origin 不增加 ch。

浏览器实测修复：直接以 Request 作为新 URL 的 RequestInit 会将普通正文变为流式上传，Chrome 连接 HTTP/1.1 时出现 ERR_ALPN_NEGOTIATION_FAILED。因此仅 Request 对象路径先读取精确正文为 Blob，再提交；保留原 multipart boundary、RequestInit 覆盖项和取消信号，取消时终止正文读取。该路径会完整缓冲正文；普通 URL + FormData 调用保持原对象，不增加这层缓冲。

普通 Key 和托管 Key 使用相同规则，不为渠道分析刷新或重新签发 Key。不再发送 `client_source/client_platform/client_environment`，不增加来源 header，不修改供应商模型 body。
