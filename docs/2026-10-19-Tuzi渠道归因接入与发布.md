# OpenTu 对接 Tuzi 渠道分析 v2.2

本实现使用每次模型请求的 query `ch`。已由用户确认按 v2.2 实施，并已部署到指定测试平台，不调整 Key 发放、复用、账户、鉴权或计费。远程没有 dev 分支，已同步实际开发分支 origin/develop 至 `26d88768`，PR 分支为 `codex/opentu-client-channel-v22`；从原工作区只提取渠道归因相关改动。

## 渠道与注入边界

| 运行 origin | ch |
| --- | --- |
| `https://opentu.ai` | 1 |
| `https://pr.opentu.ai` | 2 |
| HTTP(S) localhost / 127.0.0.1 / IPv6 loopback | 2 |
| 其他 / native scheme | 0 |

3/4 为桌面预留，当前未启用。后缀相似域名不等于正式/测试 origin。ch 可伪造，仅用于业务分析，不作为身份、安全或计费依据。

`tuzi-client-attribution.ts` 读取渠道，仅对 `tuzi-api-endpoints.ts` 中精确受信或当前部署配置的 Tuzi API origin 注入；不使用宽泛子域匹配。已存在的所有 ch（含编码键名）先删除，再加单个当前值。其他 query 原字节、hash、正文、请求头、显式 0/false 和取消信号保留。

接入点覆盖共享 provider transport、独立文本/图片/视频/音频、模型插件及工作流本地调用。插件先序列化 params 再去重 ch。启用本地代理时先标记内层目标，再包代理，已有代理不重复嵌套；Request 对象保留正文/头/信号。签名素材下载、WebDAV 和第三方 origin 不增加 ch。

浏览器实测修复：直接以 Request 作为新 URL 的 RequestInit 会将普通正文变为流式上传，Chrome 连接 HTTP/1.1 时出现 ERR_ALPN_NEGOTIATION_FAILED。因此仅 Request 对象路径先读取精确正文为 Blob，再提交；保留原 multipart boundary、RequestInit 覆盖项和取消信号，取消时终止正文读取。该路径会完整缓冲正文；普通 URL + FormData 调用保持原对象，不增加这层缓冲。

普通 Key 和托管 Key 使用相同规则，不为渠道分析刷新或重新签发 Key。不再发送 `client_source/client_platform/client_environment`，不增加来源 header，不修改供应商模型 body。

## 服务端依赖和发布

先按 Tuzi 仓库 `docs/2026-10-18-OpenTu渠道分析实施方案.md` 完成维护窗口、主库和日志库备份、受控 schema 审计/apply、旧 writer 停止及新服务启用边界初始化，再发布 OpenTu。审计命令为 `go run ./cmd/db-migrate --type mysql --client-channel-schema`；真正 apply 需要维护窗口和 `ALLOW_BLOCKING_DB_MIGRATION=true`。本次已在指定 PostgreSQL 测试平台按该顺序执行，生产环境尚未执行。

Tuzi 成功鉴权后记录并剥离 ch，供应商只收到原协议。日志/facts 存整数 ch，异步提交 snapshot 显式保存 0；后续轮询/补扣/退款继承提交渠道。启用前历史、旧任务晚完成和晚退款不补入新渠道统计。

经营分析 API 为 `/api/admin/analysis/client-sources`，默认正式网页，支持 0/1/2/all、模型搜索/20 条分页和日周月。只统计已闭合自然日，返回有效半开日期区间、汇总更新时间和日志开关。超出滚动窗口的异步完成继续回算提交日，统计非实时。
