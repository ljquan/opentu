## 问题与复现

任务队列中的一个图片任务可以同时保存多个结果 URL。用户只点击一次该任务的“插入”，任务面板仍会把 `result.urls` 展开为多个画布元素。

MJ 任务常见为单任务返回 4 张图片，因此问题表现为：

1. 打开任务队列，找到标记“4 张”的已完成 MJ 图片任务。
2. 点击一次该任务右侧的“插入”。
3. 页面提示 `Cannot read properties of undefined (reading 'clientWidth')`，结果未插入画布。

这里的“单次点击”不等于“单个结果”。故障由任务的结果数量触发，而不是由用户是否多选任务触发。

## 根因链路

1. `TaskQueuePanel` 和 `DialogTaskList` 将单个任务的 `result.urls` 映射为多个 `InsertionItem`。
2. 多 item 插入先调用 `stageCanvasInsertion`，通过 `createBoard([])` 创建临时画板，准备全部元素后再提交到真实画板。
3. 临时画板是纯数据对象，没有 React Board 的 DOM 容器。
4. Plait 0.84 的 `DrawTransforms.insertImage` 即使收到明确 `startPoint`，仍会先读取 `PlaitBoard.getBoardContainer(board).clientWidth/clientHeight`。
5. 临时画板没有容器映射，读取 `clientWidth` 时抛出异常。

因此，MJ 只是最容易出现多结果的入口，不是根因。任何返回多个图片 URL 并复用同一画布插入服务的供应商都有相同风险。

## 最终行为与范围

- 一个任务含多个图片结果时，一次点击“插入”会按结果顺序插入全部图片。
- 图片、视频和 SVG 在无 DOM 的暂存画板中使用显式坐标创建标准图片节点。
- 暂存完成后仍统一提交到真实画板；任一后续资源准备失败时，真实画板不留下前面已准备的半成品。
- 真正只有一个结果的图片或视频继续使用原 Plait 插入路径。
- 普通单图、拖拽、选中、Frame 和思维导图图片设置逻辑不变。
- 不增加 MJ 模型、分组或供应商特判；GPT Image、Gemini 和自定义 HTTP 等多 URL 图片任务共享修复。

本次不修改生成请求、供应商路由、任务数量、结果缓存格式或任务队列持久化。

## 关键实现

### 无 DOM 图片节点插入

`packages/drawnix/src/data/image.ts` 新增 `insertImageNodeAtPoint`。节点结构与 Plait 0.84 的运行时实现一致：

```ts
{
  id,
  type: 'image',
  points: [startPoint, endPoint],
  url,
}
```

该函数使用 `idCreator` 和 `Transforms.insertNode`，不读取容器尺寸，也不绑定真实画板 DOM。

### 暂存路径显式启用

- `insertImageFromUrl` 和 `insertVideoFromUrl` 追加 `insertWithoutBoardHost` 可选参数，默认不启用。
- `stageCanvasInsertion` 只在临时画板中传入 `true`。
- SVG 暂存复用同一节点构造函数。
- 单 item 分支不传该参数，继续调用 `DrawTransforms.insertImage`。

### 原子准备边界

多 item 在临时画板中依次完成缓存、加载校验、尺寸和元数据处理。全部成功后，`commitStagedCanvasInsertion` 才把节点复制到真实画板。准备阶段后续 item 失败时，真实画板保持原样。

## 性能与安全边界

- 仍按顺序准备媒体，不新增并行持有多个大 Blob 的路径。
- 不复制媒体二进制，只复制最终画布节点数据。
- 临时画板不借用真实画板 DOM WeakMap，避免不同插入任务共享可变宿主状态。
- 新参数追加在已有参数末尾，既有调用默认行为不变。
- 缓存、图片加载校验、尺寸计算、埋点、元数据绑定和画板切换保护继续复用原逻辑。

## 一句话结论

单次点击一个任务也可能插入多个结果；多结果现在可在无 DOM 临时画板中安全准备，再统一提交到真实画板，不再因读取 `clientWidth` 失败。
