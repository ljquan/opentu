# 图片 Request ID 与网络中断结果恢复交接文档

**日期**：2026-08-07

**适用分支**：`codex/image-network-recovery`

**基线**：`origin/develop` `f7a1e3ad`

**关联 QA**：[图片 Request ID 与网络中断结果恢复人工测试文档](../qa/2026-08-07-图片请求ID与网络中断结果恢复-人工测试文档.md)

## 问题

可信 Tuzi 同步图片请求可能已被上游接收，但页面刷新、网络中断或成功响应体读取中断会让浏览器无法确认结果。如果直接重发非幂等 `POST`，可能造成重复生成和重复计费；如果直接失败，已生成的结果又无法回到原任务。

同时，取消、删除、重试、同 ID replacement 和页面恢复可能与旧请求的迟到回调并发，需要阻止旧结果覆盖新尝试或释放新执行实例的资源。

## 复现路径

### 路径 1：正式提交结果未知

1. 提交可信 Tuzi 同步图片生成或编辑请求；
2. 在上游接收 `POST` 后中断连接，或使成功响应体在读取完成前中断；
3. 观察原任务是否被重发、直接失败或永久停在处理中。

### 路径 2：提交后刷新

1. 确认正式图片 `POST` 已发出；
2. 在结果返回前刷新页面；
3. 观察页面是否重新提交图片任务，以及原卡片能否收到结果。

## 核心流程

```text
正式 POST 前条件持久化
  -> 只提交一次
  -> 正常响应：沿用原完成流程
  -> 明确失败/取消：沿用原终态
  -> 可恢复的结果未知：PROCESSING + POLLING
       -> 使用同一 submissionRequestId 只读查询
       -> processing：有界退避后继续
       -> succeeded：缓存/远程 URL -> 原卡片与任务完成
       -> failed/原 15 分钟截止：明确失败
```

## 最终行为

### 1. 提交身份在 `POST` 前持久化

- 首次提交使用任务 ID 作为 `submissionRequestId`；重试保持任务 ID，但生成新的提交 Request ID。
- 正式请求前以条件事务写入 `submissionRequestId`、`imageSubmissionAttempted=true`、实际 `invocationRoute`/binding 和 `SUBMITTING` 阶段。
- `X-Request-Id` 仅发往可信 Tuzi 同步图片目标。普通节点通过固定白名单同源代理保留原 Token、计费和权限域；兼容节点保持直连。
- GET/HEAD 和第三方绝对 URL 不携带任务 Request ID，恢复查询会清理残留的同名请求头。
- 图片非幂等 `POST` 只提交一次。结果未知、5xx 或携带有效 Request ID 的 404 都不会跨节点重发。仅幂等 GET/HEAD 保留网络 fallback；未携带有效 Request ID 的图片端点收到明确 404 时，才沿用原端点 fallback。

### 2. 仅可恢复的同步图片请求进入轮询

- 只有可信 Tuzi 同步 `images/generations|edits` `POST`，且没有自定义 `pollPathTemplate`，才有恢复资格。恢复资格以最终 prepared URL、Header 和实际 binding 为准。
- 仅 fetch 级网络中断，或成功响应体在完整读取前中断，才可标记为“提交结果未知”。
- 明确 HTTP/业务失败、正常 EOF 后的完整非法响应、用户取消继续使用原错误语义，不进入恢复。
- `/videos`、Google `generateContent`、带自定义轮询路径的 binding 和非 `POST` 图片协议不进入该同步恢复状态机。

### 3. 刷新恢复保留原截止时间

- 启动恢复仅识别图片、`PROCESSING`、无 `remoteId`、存在显式 `submissionRequestId`、已提交标记和可信调用路由的任务。
- 只有恢复候选需等待设置管理器完成敏感字段解密，无关任务不被阻塞。
- 等待期间保留原 `startedAt`，仅缺失时回退 `createdAt`，不重置或延长现有 15 分钟截止时间。
- 设置初始化超时写入 `RECOVERY_TIMEOUT`；reject 或恢复路由无法解析写入 `RECOVERY_ROUTE_UNAVAILABLE`，不留下永久处理中的任务。
- 缺少新提交元数据的旧任务不使用任务 ID 猜测恢复，也不自动重提。

### 4. 只读轮询、缓存和终态写回均受控

- 每任务最多一个轮询条目，使用小型并发池、FIFO 队列、请求超时和有上限退避。并发槽同时覆盖结果查询、远程图片下载和终态写回。
- 查询优先使用原配置节点，仅在网络错误、404、408、425、429 或 5xx 时切换可信查询节点。`processing_or_not_found` 会结束当轮并等待下一次，不在同一轮扫完所有节点。
- 恢复响应最多 256 KiB；返回的 `request_id` 存在时必须与当前提交一致；结果 URL 仅接受无凭据 HTTP(S)。
- 恢复成功复用现有缓存和任务完成流程。缓存失败或超时时，使用已验证远程 URL 完成，不丢弃可用结果。
- 终态写回使用有界 watchdog 和退避，且任务最多一个在途写回 Promise；已观测到的成功或失败优先于截止时间。

### 5. 执行实例所有权阻止旧回调覆盖

- IndexedDB 终态事务校验 Request ID、原始开始时间和非终态状态，第一个合法终态生效。
- 每个内存任务实例拥有不持久化的生命周期令牌。重试、同 ID replacement、取消、删除失败回滚等会换代，旧进度、remote ID、缓存结果、终态和 `finally` 清理均不能操作新实例。
- Hook 等待队列保存任务快照与当时令牌；出队时重新读取当前任务并校验令牌与状态。已取消队列项不会发起请求，replacement 只执行新参数。
- 删除操作保留 tombstone，直到同任务已串行化写入排空；全部清空成功后保持写入暂停，阻止排队的旧写入复活任务。
- 安装同 ID 新对象前，先停止旧图片恢复和旧执行；取消、删除、重试或卸载会取消在途缓存下载并清理定时器、队列引用和 `AbortController`。

### 6. 响应体与 Custom HTTP multipart 资源有界

- 显式使用受控非流式 reader 的 provider 响应，成功体最多 64 MiB，错误体最多 1 MiB，并继续受原请求硬超时和用户取消约束。超过声明或实际字节上限会立即取消 reader。
- Custom HTTP multipart 图片来源仅允许有效图片 data URL、同源 HTTP(S)/blob URL，或无用户名密码且非 localhost/私网/链路本地目标的跨源 HTTP(S)。
- 跨源读取固定使用 `credentials=omit`、`referrerPolicy=no-referrer`、`redirect=error`，且必须是 `image/*` MIME。
- 单文件最多 20 MiB，每表单最多 16 个文件、64 MiB 文件数据和 1 MiB 文本数据。每个文件使用剩余总预算校验声明长度和实际流字节，初始缓冲最多 64 KiB，并按顺序处理。
- 任务取消会立即中止当前 multipart 下载，且不再发送 provider `POST`。

## 范围边界

- 不在健康正式请求期间并行轮询。
- 不猜测或恢复缺少新提交元数据的旧任务。
- 不延长现有 15 分钟任务时限，不提供 24 小时补偿。
- 不自动重提图片生成 `POST`。
- 不新增任意地址代理，不向第三方发送 Tuzi Token 或 Request ID。
- 不新增用户界面，原卡片、批量预览和任务队列继续使用现有完成流程。

## 剩余风险

- `processing_or_not_found` 不证明请求一定存在，因此系统只读等待到原 15 分钟截止，不自动重提。
- 上游多节点的数据同步可能存在短暂延迟，查询切换必须继续保持可信节点白名单。
- 刷新后的配置、Token 或 binding 已不可用时，任务会明确失败，无法找回上游结果。
- 完整端到端结论仍需按关联 QA 在实际部署环境执行，并对 Request ID、POST 次数和结果 GET 进行脱敏记录。

## 一句话结论

可信同步图片请求在网络结果未知或页面刷新后，会使用原 Request ID 只读找回结果，且不重复提交、不泄露凭据、不允许旧执行覆盖新任务实例。
