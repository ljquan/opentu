## 生产迁移与故障处理

1. 在测试环境从生产备份副本演练 `pnpm db:migrate`，核对旧数据及新版本标记。
2. 用迁移账号完成 DDL，再用只具备必要 DML/版本读取权限的账号启动 API。命令只读取进程环境，不自动加载 `.env` 文件。
3. 未迁移或数据库不可用时阻止发布，不通过访问线上 API 触发建表。
4. 发现 `UPSTREAM_OUTCOME_UNKNOWN`、超时或未知执行错误时，先核对上游记录、结果与费用；不能直接重新提交。
5. 数据库迁移本次只有非破坏性增量；回退应用时保留新增表列，不用删除表列作为自动回滚方式。
6. SSH 发布前由可信渠道确认主机指纹并填入 known_hosts；不恢复关闭主机验证的参数。

## 后续架构选择

现有 `add-server-generation-task-gateway/design.md` 的基线是 Vercel Functions + Neon，但对象存储和计费接口尚未选定。本轮未擅自替换此方向。以下选项需要项目负责人确定后再进入完整企业链路实施。

| 方案 | 实现复杂度 | 运行性能 | 扩展性 | 维护难度 | 潜在坑点 |
|---|---|---|---|---|---|
| A：保留 Vercel + Neon，接对象存储与持久任务服务 | 中，沿现有设计补齐 | 前端分发方便，长任务需外置 | 可独立扩任务量 | 中，较少基础设施运维 | 函数时限、平台费用、区域和连接限制 |
| B：模块化 API + 独立 worker + PostgreSQL + 对象存储 | 中高，增加运行与部署单元 | 长任务和连接生命周期更可控 | API/worker 分别扩容 | 中高，需要备份、监控和值班 | 队列和数据库单点、升级与故障接管责任 |

| 计费方案 | 实现复杂度 | 运行性能 | 扩展性 | 维护难度 | 潜在坑点 |
|---|---|---|---|---|---|
| 现有 Tuzi 余额 | 中，前提是提供 reserve/settle/release 契约 | 依赖外部接口延迟与限额 | 受接口能力约束 | 中，复用现有账户 | 仅能读取余额不足以实现计费；幂等与对账必须明确 |
| 独立钱包账本 | 高 | 可控制事务与用量结算 | 高 | 高，资金核算责任增加 | 充值、退款、并发扣费、财务和合规流程 |
| 首期仅明确免费的模型 | 低，但企业安全链路仍需完成 | 不需要余额扣减，但仍受供应商成本约束 | 适合受控试运行 | 低至中 | 不能把付费模型伪装成免费；必须有平台预算和滥用控制 |

下一批应先收敛 Web Lint 和 Drawnix 历史测试，再按所选基础设施实施账户/租户数据归属、持久任务、媒体归档、配额及计费，最后完成并发、断网、进程中断、恢复和生产发布演练。原报告的上线检查表仍然有效。
