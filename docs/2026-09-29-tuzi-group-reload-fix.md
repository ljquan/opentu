# Tuzi 关联账户新增分组刷新恢复修复

## 问题与原因

用户报告：关联 Tuzi 账户后添加分组，离开页面再返回或刷新时，新增分组消失。

本地代码确认存在以下恢复缺陷，尚未在用户线上账号复现，不能据此判定服务器令牌已被删除：

- iframe 启动时账户握手可能尚未完成，启动同步会被跳过。首次握手为隔离账户清理托管供应商后，没有在 ready 事件中恢复供应商和模型。
- 普通供应商的账户核验状态只在内存中，重载后需要重新核验。
- 原同步异常路径把临时网络错误也当成失效，删除托管供应商及模型目录。
- 添加分组使旧同步失效后，新请求可能继续复用旧 Promise。仅校验凭证的同步也可能通过缓存阻止完整模型恢复。

## 修复

- 账户握手 ready、页面重新挂载、窗口恢复焦点和页面重新可见时触发同步。
- 等待本地设置初始化和令牌解密后再核验；保留账户边界清理，避免复用其他账户的托管密钥。
- 临时同步异常保留本地配置并允许重试；只有明确的账户或凭证失效才清理托管供应商。核验失败仍不能绕过发送检查。
- 同步去重和缓存区分账户、系统令牌、分组及供应商状态、失效版本、是否需要模型发现。

## 验证

- 11 个相关测试文件共 108 项通过，覆盖握手、账户隔离、供应商复用、请求门禁、令牌选择、模型选择和同步恢复。
- 本次直接修改的两个测试文件共 15 项通过。
- TypeScript、变更文件 ESLint、生产 Vite 构建、`git diff --check` 通过。构建仍有已有的包体积和动态导入警告。
- Chrome 使用最终生产构建，在本地 iframe 宿主中操作真实 UI。父页面协议和 Tuzi API 使用测试数据：创建“绘画回归” → 移除 iframe 模拟切页 → 返回重新挂载 → 刷新，分组与模型目录均保留，令牌只创建一次，未捕获页面脚本异常。
- 注入旧托管分组并刷新后，分组和模型可以重新恢复。

浏览器验收脚本和日志：`/tmp/opentu-group-reload.cjs`、`/tmp/opentu-group-browser.log`；截图：`/tmp/opentu-group-created.png`、`/tmp/opentu-group-reloaded.png`。

本轮仅修复并验证本地 OpenTu，未修改 Tuzi 后端，未部署服务器，未进行线上账号或真实生成计费请求验收。
