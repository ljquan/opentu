## 2. 原方案与建议方案

| 方面 | 当前方案：根据有无 Key 决定关联 | 建议方案：嵌入身份、账户状态、供应商配置分别管理 |
| --- | --- | --- |
| 优势 | 独立版手动供应商可直接使用，判断简单 | 嵌入版始终要求关联当前 Tuzi 账户，能解释每个等待或失败状态 |
| 缺点 | 旧 Key 可绕过新账户关联；连接错误会切换产品模式；添加分组与首次配置混用 | 需要统一发送前检查、梳理页面返回位置和账号切换竞态 |
| 适用场景 | 独立 OpenTu，自行管理供应商 | 已部署在 Tuzi API 内的 OpenTu，同时保留独立版流程 |
| 维护成本 | 初期低，后续靠多个入口补判断，容易不一致 | 初期中等；后续由统一状态和统一检查维护 |
| 风险 | 误用旧账户 Key、菜单消失、操作完成后跳错页面 | 修复时可能漏掉发送/重试入口，需覆盖这些入口和双账号切换 |

建议采用第二种。用户已明确嵌入模式必须关联账户；保留手动 Key 不能作为跳过账户关联的依据。

## 3. 首次进入与发送

1. OpenTu 与父页面进行只读身份握手；验证父窗口、Origin、请求 ID、协议版本和 Tuzi 环境标记。
2. 确认在 Tuzi 中且未登录：显示登录引导，由父页面完成登录。
3. 已登录但没有系统令牌：自动打开“关联 Tuzi 账户”弹窗，显示当前账户、说明和“创建并关联”按钮。仅在点击确认后创建系统令牌。
4. 系统令牌已存在：直接使用父页面提供的当前账户关联信息，不要求手工复制令牌。
5. 关联成功但没有当前账户可用的托管分组：进入“添加 Tuzi 分组”，默认勾选 default（仅在账户有权限时）。
6. 完成后，如果本次流程由发送触发，重新校验账户与供应商后恢复原请求一次；如果由设置或新增入口触发，只完成配置。
7. 取消弹窗可继续浏览和编辑，但后续发送仍需完成关联；不丢失提示词、附件、参数，不通过关闭弹窗绕过检查。

系统令牌用于账户关联，分组 API Key 用于模型调用，两者状态必须分别表示。

旧的手动配置可保留，但不能自动证明当前账户已经关联。完成关联后默认使用当前账户托管分组；若保留外部/手动供应商功能，应由当前账户明确选择，不能静默继承其他账户的默认选择。

## 4. 分组与令牌入口

| 入口 | 建议名称 | 具体动作 | 成功后的返回位置 |
| --- | --- | --- | --- |
| 模型选择器左下角 | 添加 Tuzi 分组 | 直接进入当前账户的可选分组，已添加项标记为“已添加” | 回到模型选择器，显示新增供应商和模型加载状态 |
| 账户页分组列表右上角 | 添加 Tuzi 分组 | 添加用户已获授权的其他分组；后台已有托管 Key 就复用，没有才创建 | 保持账户页，刷新分组列表，提示“已添加” |
| 账户页下方原“创建新的令牌分组” | 管理 API 令牌 | 打开父站 `/console/token` 的令牌管理页，用于手动创建/管理普通 API Key；建议新标签打开，保留 OpenTu 编辑状态 | 原 OpenTu 页面保持不动，不把任意手动令牌自动纳入托管列表 |

用户已确认截图中的两个入口分别为：上方“添加 Tuzi 分组”，下方“管理/创建 API 令牌”。已按这个分工实现，下方链接使用经过握手验证的父站 Origin。

现有 `GET /api/opentu/provider-groups` 只列出用户有权使用的分组；`POST /api/opentu/providers/ensure` 为所选分组复用或创建托管 Key。它们不会创建新的计费/权限分组。普通用户不能通过“新增分组”扩大权限。给同一分组另建普通 API Key 应走令牌管理；“换新 Key”仍是替换当前托管 Key 的独立操作。

## 5. 添加分组的状态与返回

- 区分 `首次关联`、`模型选择器添加`、`账户页添加` 三种入口意图，明确各自返回目标。
- 待执行导航指令只在目标组件准备好且成功应用后消费；所有指令类型统一处理。
- 后续添加操作保留已有分组及当前使用分组，仅增加新选项。取消不会改变已有配置。
- 分组确认按钮使用“添加所选分组”；首次关联最后一步可使用“完成并继续”。避免普通添加操作复用首次关联的关闭整页回调。
- 只有后台成功返回、供应商配置持久化成功后，才更新本地分组选择和显示成功。现状是在请求前保存选择，失败时会留下未真正完成的配置标记。
- 模型发现单独显示“加载中/加载失败，可重试”。它不应清除账户连接或把整个添加流程重置。
- 重试复用 ensure 的现有幂等行为；若服务端部分创建后失败，重新提交所需分组，不通过反复生成 Key 恢复。

## 6. 连接与账户边界

- `运行环境`：未确认、独立、已确认 Tuzi。
- `连接状态`：连接中、已连接、暂时不可用。
- `账户状态`：未登录、缺系统令牌、已关联。
- `分组状态`：待选择、创建中、可用、失败。
- 确认过的 Tuzi 环境在同一页面生命周期内不因超时、5xx、分组加载失败降级为独立版。账户菜单保留并显示错误和重试；连接未验证时阻止受保护请求。
- 未登录/会话失效只改变账户状态，不改变运行环境；网络失败不能被当作退出登录或独立环境。
- 首次握手时，从未确认过的普通第三方 iframe 才允许按兼容策略回到独立流程；可信 Tuzi 父页面返回的业务错误应明确显示，不当作“不支持集成”。
- 账户切换递增会话版本，清除或隔离旧账户托管凭据，取消待发送请求；旧异步回包不得覆盖新账户。
- 分组选择、当前分组和手动供应商使用选择按 Tuzi 站点与用户 ID 隔离。当前只按用户 ID 的本地记录需考虑不同 Tuzi 站点 ID 相同的情形。
- 所有发送/重试/待发恢复入口复用同一检查；无有效凭据时不得回退到历史 `gemini.apiKey`。系统令牌继续仅存在于内存，不写 URL、日志或磁盘。

## 7. 验收要求

1. 新用户已登录、无系统令牌，浏览器保留旧手动 Key：自动出现关联提示；确认前没有模型请求。
2. 新用户已有系统令牌、无分组：显示分组配置；成功后使用当前用户 Key。

4. 从模型选择器添加分组：直接显示分组选择，完成后回到模型选择器。
5. 图四两个入口确实执行不同业务；新增入口不创建越权分组，不误轮换现有 Key。
6. 已连接后模拟超时、5xx、401：分别展示重试或登录引导，均不变成独立版。
7. 创建中切换账户、迟到回包、重复点击、取消、关闭后恢复：不串号、不重复发送、不误用旧 Key。
8. 独立 OpenTu 的手动供应商流程正常，未嵌入 Tuzi 时不强制 Tuzi 关联。
9. 在真实浏览器以两个测试账户完成上述流程，记录请求使用的账户/分组标识和状态，不记录令牌明文。

## 10. 第二轮：已有供应商令牌复用（用户已确认）

2026-09-28，用户确认优先核验并复用现有供应商，不因账户关联重复创建令牌。本轮在上一轮修复上增加：

- Tuzi API 新增 `POST /api/opentu/providers/verify`，经账户认证后，仅从该账户未删除的令牌中匹配 SHA-256 Key 指纹。每批最多 100 项，返回归属匹配结果、实际分组、令牌名称、状态和限制，不返回 Key，不修改数据库。多分组令牌保留完整分组信息。
- 父子页面增加 `TUZI_VERIFY_PROVIDERS` / `TUZI_PROVIDERS_VERIFIED`，校验来源、请求 ID、协议和返回账户 ID。OpenTu 仅核验 API Origin 与当前 Tuzi 站点一致的本地供应商，不提交第三方站点凭据。
- 核验状态仅保存在内存，绑定 Tuzi API 站点、当前账户及本次系统令牌；修改 Key 或地址后必须重新核验。使用 `@noble/hashes` 计算指纹，以支持测试服 HTTP 局域网页面，不依赖安全上下文限定的 Web Crypto。
- 每个通过核验且启用的供应商保留原 ID、名称、Key、模型目录和自定义配置。同组多个供应商不合并，按供应商 ID 记录当前选择。内置供应商的自定义名称和图标也保留。
- 账户关联时发现可用供应商就显示复用结果并允许完成，无须再建分组令牌。分组创建仅为未覆盖的明确选择创建托管 Key。后台同步不会自动替换已经识别过的失效普通令牌；用户主动添加分组时可以选择创建托管替代项，原普通令牌仍保留。
- 过期、停用、额度/次数耗尽、无分组权限、非本账户或已删除等结果分别显示，有效项继续可用。普通令牌的模型/IP/额度等限制保持原样，由 Tuzi API 正常请求鉴权执行，关联核验不等于任意模型调用均被授权。
- 普通令牌行显示“已关联 · 复用已有令牌”，提供“管理令牌”链接，不提供托管令牌换新操作。自动模型列表请求也受账户核验控制。
