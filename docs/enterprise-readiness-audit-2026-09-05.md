## 1. 上线结论

**当前不建议直接作为承载真实企业数据和平台生成费用的公网多用户正式服务上线。**

项目已具备较丰富的创作功能和一定工程基础，但整体仍是“浏览器本地优先的创作工具 + 正在接入的服务端管理与生成能力”。主要差距集中在安全边界、账户数据隔离、服务端生成闭环、故障恢复和发布质量门禁。增加更多界面和模型数量，不能解决这些问题。

本报告整理了 **18 组问题：9 组 P1、9 组 P2**。这些是合并后的整改主题，不代表 18 个独立可利用漏洞。另列出上线前必须核实的外部条件。

- **P1：正式上线前必须解决或从生产产品中明确关闭相关能力。** 包含已复现安全缺陷和已确认的生产能力缺口。
- **P2：上线准备阶段完成，或通过明确的规模限制、功能限制和补偿措施后安排整改。**
- **待核实：仓库不能证明的外部环境状态。** 不能因为仓库中没有实现，就断言外部系统也没有。

未发现足以定为“无需前置条件即可完全接管服务”的 P0 证据。本结论也不构成完整渗透测试或上线认证。

## 4. P1 详细发现

### 01. 画布文件导入存在 HTML 注入执行路径

**位置：** [导入校验](/D:/工作/Opentu/packages/drawnix/src/data/drawnix-data-validation.ts:3)、[导入入口](/D:/工作/Opentu/packages/drawnix/src/data/blob.ts:48)、[组件错误展示](/D:/工作/Opentu/packages/drawnix/src/components/tool-element/tool.generator.ts:300)。

校验仅检查顶层类型、`elements` 是否为数组、`viewport` 是否为对象。未知工具组件的 `element.component` 被直接拼入 `container.innerHTML`。因此包含 HTML 事件属性的组件名称可以通过导入校验，并在错误展示时执行脚本。

**验证：** 使用实际校验函数和从源码读取的实际赋值语句，在隔离 jsdom 中放入无害标记；得到 `importAccepted=true`、`scriptMarker=1`。未操作生产页面，未读取任何用户凭据。该验证证明校验和危险渲染点之间的缺陷；完整浏览器导入回归仍需补齐。

**影响：** 用户导入不可信画布或恢复相关数据时，同源脚本可读取本地作品，接触浏览器可用的凭据，并调用会话权限允许的 API。是否受到额外 CSP 阻拦取决于实际部署，当前配置不能作为可靠补偿。

**建议与验收：** 错误内容改为文本节点；对导入元素实施有版本的 schema 和组件白名单；限制体积、嵌套深度及 URL 协议。以恶意组件名、非法 URL、畸形元素做真实浏览器导入回归，确认无事件执行且正常文件兼容。

### 02. 工具消息可以由不匹配的窗口来源触发

**位置：** [消息接收](/D:/工作/Opentu/packages/drawnix/src/services/tool-communication-service.ts:127)、[消息校验](/D:/工作/Opentu/packages/drawnix/src/services/tool-communication-service.ts:176)、[生成处理器](/D:/工作/Opentu/packages/drawnix/src/plugins/with-tool.ts:141)。

消息校验检查字段和工具 ID 对应的 iframe 是否存在，但没有检查 `event.origin` 或 `event.source === iframe.contentWindow`。发送端还使用 `postMessage(..., '*')`。现有消息处理器能够创建图像生成任务。

**验证：** 在隔离 DOM 中实例化实际服务，发送来自 `https://untrusted.example`、`source=null` 的合法格式消息，注册的无害处理器仍被执行。

**前置条件：** 攻击方需要获得目标窗口引用，并知道或可推断一个存在的工具 ID。嵌入页面天然获得自己的工具 ID；不应把“工具存在”视为授权。该问题不是任意网站无条件控制所有用户。

**建议与验收：** 绑定窗口来源和精确 origin；给工具分配明确能力，生成等消耗性操作单独授权；校验消息 payload 和回复关联关系。对于 sandbox 的 opaque origin 使用受控握手/能力令牌设计。跨源、错误 source、未授权操作均应被拒绝。

### 03. 供应商 SSRF 防护未覆盖完整地址与 DNS 场景

**位置：** [目录请求地址校验](/D:/工作/Opentu/api/_lib/provider.ts:39)、[目录请求](/D:/工作/Opentu/api/_lib/provider.ts:129)、[生成出站校验](/D:/工作/Opentu/api/_lib/generation/outbound.ts:36)。

供应商目录请求只排除部分 RFC1918/回环 IPv4，未完整排除链路本地、IPv6 私网等地址。生成请求的校验更完整，但两套实现不一致；两者都在 DNS 预检查之后让 `fetch` 自行建立连接，预检查与真实连接地址未绑定，存在 DNS 重绑定窗口。

**验证：** 使用实际 `fetchProviderModels`，在 production 模式将 DNS 模拟解析为 `169.254.169.254`，仍然到达 mock fetch。没有真实访问内网或云元数据服务。该结果证明拦截缺口，不代表真实云元数据端点一定可通过 HTTPS 和当前固定路径读取。

**前置条件：** 此路径通常需要供应商管理权限或可影响所配置域名。应防止受损管理员或供应商域名将服务器变成内网请求代理。

**建议与验收：** 共用经过充分测试的出站策略，完整处理 IP 表达形式、全部 DNS 结果、私网/保留地址和重定向；结合地址绑定或部署出口网络限制。测试应覆盖 IPv4/IPv6、链路本地、映射地址和 DNS 重绑定。

### 04. 服务端生成、上传和计费迁移尚未形成生产闭环

**位置：** [迁移任务清单](/D:/工作/Opentu/openspec/changes/add-server-generation-task-gateway/tasks.md)、[浏览器接收托管令牌](/D:/工作/Opentu/packages/drawnix/src/services/tuzi-session-api.ts:215)、[设置持久化](/D:/工作/Opentu/packages/drawnix/src/utils/settings-manager.ts:1491)、[计费边界](/D:/工作/Opentu/api/_lib/generation/repository.ts:131)。

前端源码未找到对 `/api/generation/tasks` 的调用。当前仍从 Tuzi 接收用户托管 API Token，在浏览器供应商配置中使用，并同步到本地执行所需配置。服务端网关目前只有文本和图片适配，B2 异步媒体/上传、B3 前端迁移、生产余额预占与结算仍未完成。

**必须区分：** 这些浏览器 Token 不等于已经泄露了服务端加密保存的供应商主密钥；localStorage 设置也已有敏感字段加密。但客户端可使用、解密的凭据无法成为防止客户端绕过策略的安全边界。Tuzi 外部已有的令牌额度/计费能力不在本仓库内，不能断言完全没有计费。

**建议与验收：** 选择一个正式企业部署路径，将生产允许的生成能力全部接到受认证服务端；统一模型授权、额度、任务归属、结果与错误协议。付费能力必须通过预占、结算、释放、重试及取消对账用例，未完成时明确关闭，不把 `free` 当作扣费替代方案。

### 05. 工作区和本地任务未按账户隔离，企业数据持久性不足

**位置：** [固定工作区数据库](/D:/工作/Opentu/packages/drawnix/src/services/workspace-storage-service.ts:115)、[按 board.id 保存](/D:/工作/Opentu/packages/drawnix/src/services/workspace-storage-service.ts:372)、[固定任务数据库](/D:/工作/Opentu/packages/drawnix/src/services/app-database.ts:13)、[浏览器关闭快照](/D:/工作/Opentu/apps/web/src/app/app.tsx:175)。

工作区使用固定的 `aitu-workspace`，任务使用 `aitu-app`，画板记录和本地缓存没有以账户/租户为命名空间。作品入口从这些本地存储加载。相同浏览器配置切换账户时，身份变化不会自然形成数据边界。

**影响：** 共享电脑存在前一用户作品继续可见的风险；浏览器数据清理、设备损坏或不同设备访问时，无法依赖服务端恢复全部作品。项目已有手动备份和 GitHub 同步，但它们不等价于默认启用、可审计的企业备份和集中访问控制。此处不是断言不同设备上的用户可直接互读数据库任务。

**建议与验收：** 明确组织、用户、项目、作品的所有权模型；服务端持久化作品元数据和媒体对象；本地缓存带身份命名空间并在退出/换号时重建访问上下文。验证同设备 A/B 换号、不同设备同步、权限撤销、误删恢复、浏览器清空后的恢复。

### 06. 任务在 submitting 状态中断后无法恢复

**位置：** [同步执行上游调用](/D:/工作/Opentu/api/_lib/generation/service.ts:41)、[幂等重试只处理 queued](/D:/工作/Opentu/api/_lib/generation/service.ts:93)、[70 秒租约](/D:/工作/Opentu/api/_lib/generation/repository.ts:258)。

创建请求直接等待上游生成。租约写入到数据库，但没有发现处理过期租约的执行器；领取条件只允许 `queued`。进程重启、函数被终止或执行中数据库故障后，任务会停在 `submitting`。同幂等键重试仅返回原状态，GET 也只读取，不推进恢复。

**影响：** 用户看到永久处理中；上游可能已经消耗费用或完成生成，平台却未保存结果。用户换幂等键重做可能产生再次消费。取消状态也依赖原执行最终完成，无法解决执行进程已经消失的情况。

**建议与验收：** 引入持久队列/独立 worker 或可靠任务编排，明确超时、租约续期、恢复、上游幂等能力和结果核对。必须在“上游受理后、结果落库前”强制终止进程，验证任务最终可对账收敛；禁止简单地把所有过期任务重新提交。

**位置：** [xlsx 锁定版本](/D:/工作/Opentu/pnpm-lock.yaml:6994)、[mermaid 锁定版本](/D:/工作/Opentu/pnpm-lock.yaml:5206)、[表格读取](/D:/工作/Opentu/packages/drawnix/src/components/ttd-dialog/batch-image-generation.tsx:1664)、[宽松 Mermaid 渲染](/D:/工作/Opentu/packages/drawnix/src/components/chat-drawer/MermaidRenderer.tsx:109)。

### 09. 静态部署方案无法单独运行当前服务端能力

**位置：** [Dockerfile](/D:/工作/Opentu/Dockerfile:15)、[Vercel 配置](/D:/工作/Opentu/vercel.json)、[Netlify 配置](/D:/工作/Opentu/netlify.toml)。

Docker 最终镜像只复制 `dist/apps/web` 并运行静态 HTTP 服务，没有 Node API 执行环境。Netlify 配置也没有展示 Vercel 风格 `api/` 的函数适配。用户按这些部署路径部署，不能仅凭同一份静态产物获得管理、目录及生成 API。

Vercel 可能通过文件约定部署 API，但真实路由、Cookie、数据库连接、函数时限和请求/响应大小尚未验证。不能因为本地 Vite 页面可打开，就认为生产服务端链路已可用。

**建议与验收：** 指定正式支持的部署拓扑及 API/Worker 运行方式，其他部署路径注明能力边界。在全新环境执行完整安装和登录、目录、管理、生成、查询、取消测试，检查错误路由返回 JSON 而非 SPA HTML；备份与回滚也纳入部署验收。

## 5. P2 详细发现

### 10. 任务完成记录和用量写入没有事务

**位置：** [completeTaskSuccess](/D:/工作/Opentu/api/_lib/generation/repository.ts:283)。

先将任务改为 succeeded 并清空 lease，再更新 attempt、写 usage。如果后两步失败，服务层进入失败补偿，但 lease 已清空，任务更新无法匹配；可能出现任务成功、attempt 失败、usage 缺失。当前付费功能未开放，所以这里不是已发生的资金损失证据，但它会直接影响未来结算可靠性。

**建议/验收：** 用数据库事务保证状态、attempt、usage 的一致提交；外部计费用持久化事件和幂等补偿。对每个写入点注入失败，验证不存在不可解释的半提交状态。

### 11. 数据库迁移由线上请求执行

**位置：** [ensureSchema](/D:/工作/Opentu/api/_lib/db.ts:41)、[公开目录入口](/D:/工作/Opentu/api/catalog/models.ts:10)。

首次调用会连续执行建表、建索引和 ALTER TABLE；Promise 只在当前进程中去重。多个冷启动实例可能同时执行 DDL，应用账号需要拥有结构修改权限，匿名目录访问也可能触发初始化。没有版本化迁移记录和独立迁移阶段。

**建议/验收：** 发布阶段使用版本化迁移工具，迁移角色和运行角色分开；执行兼容新旧版本的扩展/收缩迁移。验证空库初始化、旧库升级、并发启动及失败恢复。

### 12. 供应商模型同步存在半更新和规模问题

**位置：** [syncProviderModels](/D:/工作/Opentu/api/admin/providers/[...path].ts:157)。

按模型逐个等待 INSERT/UPDATE，最后再将未出现的模型设为不可用。大量模型需要大量串行数据库往返；中途失败留下部分更新，重复点击或多管理员同时同步也没有按供应商互斥。整个目录并非按一次完整快照发布。

**建议/验收：** 批量 upsert、供应商级锁或任务互斥、同步批次标识和事务性快照切换。以大量模型、部分写入失败及两个并发同步验证一致性和可控耗时。

### 13. 生成结果缺少持久媒体归档和保留策略

**位置：** [结果规范化](/D:/工作/Opentu/api/_lib/generation/adapters.ts:113)、[结果及限流表](/D:/工作/Opentu/api/_lib/db.ts:103)、[用量写入](/D:/工作/Opentu/api/_lib/generation/repository.ts:316)。

图片结果可以直接包含上游 URL 或大段 base64，并整体保存到 JSONB。上游临时链接可能失效；大结果增加数据库、GET 响应、备份和内存成本。服务端任务、输入及每分钟限流桶未找到清理或归档机制。响应容许范围是否适合实际托管平台，也未验证。

**建议/验收：** 对象存储保存媒体，数据库保留受控引用、归属和校验信息；明确私有访问、签名链接、保留期、删除与备份规则；清理过期限流桶。验证上游链接过期后仍可读取作品，删除和恢复符合约定。

### 14. 请求频率限制不能控制总成本和执行容量

**位置：** [consumeGenerationRateLimit](/D:/工作/Opentu/api/_lib/generation/repository.ts:147)、[计费边界](/D:/工作/Opentu/api/_lib/generation/repository.ts:131)。

现有限制按用户、操作和分钟计数，默认每分钟 12 次，管理员至少 60 次。没有活跃任务并发上限、租户预算、供应商并发池、全站花费上限及排队背压；多个账户同时调用仍能放大负载。`free` 是平台承担成本，并不意味着上游免费。

**建议/验收：** 增加用户/组织/供应商/全局多层容量与预算约束、异常流量保护、队列背压和熔断。按目标负载确认接受、排队、拒绝和预算耗尽行为，不仅统计 HTTP 成功率。

### 15. 管理审计和集中运维观测不足

**位置：** [管理权限与写操作](/D:/工作/Opentu/api/admin/providers/[...path].ts:265)、[服务端生成错误日志](/D:/工作/Opentu/api/_lib/generation/service.ts:51)、[浏览器崩溃记录](/D:/工作/Opentu/apps/web/src/crash-logger.ts:1)。

管理入口调用 `requireAdmin` 后没有保存操作者和变更审计；供应商删除、密钥轮换、模型发布和计费模式变更缺少可追溯记录。服务端主要使用 console 日志，仓库未展示集中告警、任务积压/成功率/延迟指标和 readiness 检查。已有本地崩溃日志不能替代值班系统。

**建议/验收：** 增加结构化 request/task ID、脱敏日志、管理审计和告警；设置账户服务不可用、任务积压、上游错误、预算异常、数据库故障演练。实际托管平台已有的日志和告警需一并盘点，避免重复建设。

### 16. 发布连接信任不足，部署安全头不一致

**位置：** [SSH 配置](/D:/工作/Opentu/scripts/upload-and-deploy.js:74)、[Nginx 上传](/D:/工作/Opentu/scripts/upload-nginx-config.js:90)、[安全头配置](/D:/工作/Opentu/netlify.toml)、[Vercel 配置](/D:/工作/Opentu/vercel.json)。

SSH 脚本关闭 Host Key 校验并忽略 known_hosts；密码方式使用命令行参数。Netlify CSP 允许 unsafe-inline/unsafe-eval，HTML 专用规则只声明 frame-ancestors；Vercel 未声明对应安全头。线上实际防护是否由外部代理补充尚不清楚。

**建议/验收：** 固定并验证部署主机公钥、使用受限部署身份，统一经过功能回归的 CSP、HSTS、nosniff、Referrer-Policy 等策略。以生产响应头和实际嵌入/Worker 功能测试验证，不能只审查配置文本。

### 17. 数据规模增长和超大模块增加性能及维护风险

**位置：** [元数据扫描](/D:/工作/Opentu/packages/drawnix/src/services/workspace-storage-service.ts:448)、[定时器](/D:/工作/Opentu/packages/drawnix/src/services/tool-communication-service.ts:237)、[AIInputBar](/D:/工作/Opentu/packages/drawnix/src/components/ai-input-bar/AIInputBar.tsx)、[SW](/D:/工作/Opentu/apps/web/src/sw/index.ts)。

`loadAllBoardMetadata()` 虽然只返回元数据，但仍通过 localforage iterate 读取每条完整 Board 再丢弃 elements，不能避免大作品记录的读取和反序列化成本。工具通信服务的 setInterval 没有保存句柄，destroy 也未 clearInterval，销毁后仍保留回调和实例引用。

当前 AIInputBar 约 8,211 行、SW 约 6,833 行、task-queue-service 约 3,687 行。行数本身不是故障，但这些文件包含多个职责，会扩大一次变更的理解和测试范围。现有懒加载、分包和虚拟化应保留，不能因模块大就断言首屏一定慢。

**建议/验收：** 元数据独立存储或索引化、分页读取；清理定时器；按调用边界逐步拆分。建立按作品数量、单画布元素量、媒体体积区分的性能基线，测冷启动、切换、内存、长任务和输入响应，取得数据后再决定进一步优化。

### 18. 企业架构契约和运行资料尚未收敛

**位置：** [项目规范仍为模板](/D:/工作/Opentu/openspec/project.md:1)、[角色授权](/D:/工作/Opentu/api/_lib/auth.ts:64)、[网关后续任务](/D:/工作/Opentu/openspec/changes/add-server-generation-task-gateway/tasks.md)。

项目规范中的用途、架构、测试策略和约束仍是占位内容。应用依赖外部 Tuzi 身份，管理授权直接使用其 role 阈值；仓库中未展示组织成员、项目 ACL、企业 SSO/MFA 管理契约和本地管理员范围映射。上线方式、数据保留、备份责任、故障处理也未形成完整一致的运行手册。

**建议/验收：** 明确身份提供方与应用授权的责任边界；按实际产品合同决定是否需要租户、组织角色和 SSO，不能默认所有企业特性都要一次实现。补齐架构图、API 契约、配置清单、发布/回滚、恢复演练、安全事件流程及负责人；由非原作者按文档完成一次安装和故障恢复。

## 6. 架构方案对比

以下只做评估，**未选择并实施任何优化方案**。后续开发应由你选定方案，并按项目 OpenSpec 流程明确范围。

| 方案 | 实现复杂度 | 运行性能 | 扩展性 | 维护难度 | 潜在坑点 |
|---|---|---|---|---|---|
| A. 保留 Vercel 等托管入口，补齐托管数据库、对象存储和持久任务服务 | 中，需要补齐身份、数据和生成闭环 | 静态分发方便；长任务交给持久任务服务，受平台限制和外部调用延迟影响 | 适合逐步增长，可独立扩任务执行量 | 中，基础设施运维较少 | 平台时限、费用、区域、Cookie 与托管服务绑定 |
| B. 模块化单体 API + 独立 worker + PostgreSQL + 对象存储 | 中高，可沿现有 API 分层演进 | 连接、队列和任务生命周期更可控；是否更快需压测 | API/worker 可分别扩容，通常足够支撑初期到中期业务 | 中，需要明确部署、备份和值班责任 | 运维能力不足时，数据库和 worker 会成为单点 |
| C. 多微服务 + Kubernetes + 分布式工作流 | 高，涉及更多网络协议和服务治理 | 可细分扩容，但增加服务间延迟和运行开销 | 高，适合已有明确组织和规模边界 | 高，测试、发布、排障和资源成本显著增加 | 在规模未验证时过度设计；分布式一致性和故障复杂 |

**评审意见：** 需求合理，可沿现有代码渐进完成。近期应在 A/B 中选择，选择依据是既有部署平台、团队运维能力、任务时长和数据要求。当前没有数据证明需要 C。无论选择 A 还是 B，01–08 的安全、数据和质量问题都需要解决。

其他局部取舍：浏览器本地优先可以继续作为离线缓存，但要明确服务器权威数据与同步冲突协议；保留用户自带 Key 的独立工具模式也可以，但不能与平台托管费用的企业模式混用安全假设。

## 7. 建议整改顺序与准入标准

### 阶段一：封住明确风险，建立可信检查

完成 01–03、07–08；限制未授权工具能力和不可信导入；确认正式部署方式。验收要求是安全回归可重复执行，API/Web 类型、lint 和测试全部进入 CI，失败提交不能产出可发布生产版本。

### 阶段二：完成企业核心业务链路

完成账户/项目数据隔离、服务端任务、持久媒体、计费边界和任务恢复。最小验收链路：登录 -> 授权模型 -> 创建任务 -> 额度处理 -> 执行 -> 结果持久化 -> 换设备读取 -> 故障与取消对账。

必须测试同账户重复提交、并发重复幂等键、不同账户读写、会话过期、上游超时、上游成功但数据库失败、worker 重启和媒体过期。

### 阶段三：演练并收敛正式运行能力

完成迁移、备份恢复、日志告警、发布回滚、成本和容量演练。先确定目标规模、SLO、RPO/RTO，再决定压测负载与扩容阈值。浏览器性能应覆盖低配置设备和逐渐增长的作品库。

### 正式开放前检查表

- [ ] 所有 P1 已关闭，或相关功能已在服务端及前端同时禁用。
- [ ] 真实部署的登录/退出、Cookie、API 路由和权限隔离已验收。
- [ ] 平台付费生成有可验证的结算与补偿；未完成则保持关闭。
- [ ] 真实用户作品在浏览器清空或设备更换后可按约定恢复。
- [ ] 任务在进程中断、重试和取消后最终可收敛、可对账。
- [ ] CI 在干净 Linux 环境及正式运行版本完成检查，发布制品有版本和来源。
- [ ] 迁移、恢复、回滚和告警演练有记录及负责人。
- [ ] 已完成目标规模压测，记录延迟、积压、失败率和单任务成本。
