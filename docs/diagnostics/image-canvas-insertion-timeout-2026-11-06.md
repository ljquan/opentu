# 图片已生成但插入画布超时：定位记录

- 日期：2026-11-06
- 代码基线：`codex/fix-image-canvas-timeout`，`b742f593`（本次拉取的 `origin/develop`）
- 范围：先记录修复前的分析与复现，文末记录限定生成结果入口的修复与验收；线上部署版本尚未确认。
- 用户反馈：批量生成时相当一部分失败，重试插入也未成功；日志中的完整原图能够打开。确切数量、原图打开耗时、浏览器与系统未确认。

## 结论与证据边界

截图的“画布插入超时，可重试插入已有结果”来自前端 `executeCanvasInsertion` 的固定 60 秒总截止时间，不是生成接口错误。这个“插入”包含缓存查询、下载、缓存写入、图片加载/解码，最后才修改画布节点。

已用真实生产函数搭配模拟浏览器 I/O 和虚拟时钟，复现相同报错、可读图片未插入、重试再次失败。尤其存在无需网络请求即可触发的场景，所以不能把这个症状简单归因为用户网络问题。

这些测试确认的是程序机制，不是该线上用户的唯一根因。缓存延迟和网络延迟为注入条件，尚未测得线上实际耗时。原图可打开降低文件本身损坏或失效的可能，但外部打开图片与站内 fetch 的 CORS、Service Worker、缓存路径不同；还需要确认是否在同一台设备、同一时间测试。

## 关键调用链

生成服务返回结果 → 尝试缓存结果（失败时允许保留远程 URL）→ 完成任务 → 自动插入 → `executeCanvasInsertion` 开始 60 秒计时 → `insertImageFromUrl` 再次尝试缓存 → 加载/解码 → 检查 boardGuard → 写入画布。

### 1. 单张图的多段操作共享 60 秒，内部超时预算与之不匹配

相关代码：

- `packages/drawnix/src/services/canvas-operations/canvas-insertion.ts:68,697`：全流程 60 秒。
- `packages/drawnix/src/data/image.ts:617`：先 `cacheRemoteUrl`，再 `loadImageElementForCanvas`。
- `packages/drawnix/src/services/media-executor/fallback-utils.ts:630`：缓存目标查询、源地址查询、读取、迁移写入、写后确认等串行执行。
- `packages/drawnix/src/utils/image-operation-timeout.ts:1`：下载 30 秒、单次缓存操作 20 秒、Blob 解码 15 秒、普通图片加载 300 秒。

即使每个内部步骤都在自己的期限内完成，累计也能超过外层截止时间。最外层报错覆盖具体阶段，截图本身无法分辨卡在下载还是缓存。

### 2. 重试可能反复从头做缓存迁移

`insertImageFromUrl` 每次使用 `insert-${generateUUID()}` 作为缓存任务标识。输入仍为远程 URL 时，每次重试生成不同的稳定缓存目标。这里没有把新地址回写到原任务结果；重试入口重新把同一个完成任务交给插入流程。

在远程源已经缓存、但缓存操作较慢的场景中，第一次操作甚至已经写好了本地副本，却因最后确认超出 60 秒被判失败；下一次重试仍可生成新缓存目标，再执行一遍迁移。

这只适用于插入收到远程 URL 等相应路径，不能套用到所有已经使用本地虚拟 URL 的结果。

### 3. 合并插入的多张图共用一次 60 秒，而且串行准备、整组提交

`stageCanvasInsertion`（`canvas-insertion.ts:601`）逐张等待图片准备，最后才执行 `commitStagedCanvasInsertion`。一组五张图，每张 13 秒就会整体超过 60 秒，前四张已经准备好的图片也不会提交。

`useAutoInsertToCanvas.ts:2593` 的失败处理可把同组任务都标记为后处理失败。

这是确定的风险，但不是截图中所有图片必然共用一个预算：`image-generation-anchor-task.ts:51` 会为有独立批次槽位的任务生成独立分组键。截图不能证明线上走了合并分组路径。

### 4. 外层超时只阻止写入，没有贯穿到底层 I/O 的取消

外层 AbortSignal 被包进 `boardGuard`，没有传给 `insertImageFromUrl`、其 `cacheRemoteUrl` 调用或图片加载器。于是 UI 在 60 秒失败后，当前图片加载/缓存工作仍可继续，迟到结果被 guard 拒绝。

这保护了画布不被迟到任务污染，但不能释放所有底层等待；持续重试可能增加资源竞争。资源竞争的实际严重程度尚未测量。

另外，guard 因“已超时”返回 false 时，内层抛出的文案也是“画板已切换，取消本次插入”，因此控制台看到这条错误并不一定代表用户切换了画板。

### 5. 原图可打开不等于站内下载/缓存成功

`fallback-utils.ts:720` 的缓存下载使用 CORS fetch；直接打开图片不要求同样的跨域可读权限。缓存失败会保留远程 URL；后续 Image 加载还可能经过 Service Worker。

`apps/web/src/sw/index.ts:5997,6058,6230` 的外部图片拦截另有 15 秒超时与请求去重；`data/image.ts:226` 的远程图片重试使用原地址，不追加绕过参数。因此网络面板中的请求方式、响应头、SW 介入情况值得核查。

尚无真实故障 URL 或用户侧网络记录，不能把 CORS、CDN、SW 认定为本次根因。

## 建议修复顺序

1. 增加插入阶段与耗时记录：任务 ID、结果来源类型、缓存查询/下载/写入/解码各自耗时、批次大小、是否命中缓存及实际失败阶段；保留原始错误，避免统一超时掩盖原因。
2. 复用已经成功准备的资源，用稳定任务/结果标识或内容标识缓存；重试不要反复创建随机副本。保留离线缓存与签名 URL 失效保护。
3. 分离图片准备与最终画布提交的时间预算。给多张图提供合理的逐项预算或受控并发准备；维持现有布局、去重与画板切换保护，明确整组失败还是逐项成功语义。
4. 贯穿 AbortSignal，超时结束当前加载与可取消的网络请求；区分超时取消和切换画板。
5. 再根据故障 URL 的响应验证是否还需修复 CORS/SW 路径。单独把 60 秒改大只能缓解，不能解决重复处理与取消缺失。

## 确认线上具体原因所需的最少信息

- 一张失败任务的原始图片 URL，以及站点地址/版本；用截图任务 ID 对应同一任务。
- 在故障用户环境点击一次“重试插入”的 Network/Console 记录：先看是否有下载请求、状态码与耗时，再区分缓存/解码；不需要重新生成大量图片。
- 若结果已经是 `/__aitu_cache__/...`，应优先检查用户本地原图缓存、缩略图回退和读取耗时；若仍是远程地址，应检查缓存失败原因与插入时重复下载。

### 更新后的判断

已经从“模拟测试可触发”推进到“真实 Chrome、真实图片、真实限速可以触发”。本次下载变慢是触发条件，程序的串行缓存/加载回退、不同层级时间预算与取消策略共同决定最终失败，不能简单归为生成失败。

这仍不证明客户所有失败任务都是同一个原因。尤其客户的“重试仍不成功”尚未在其真实环境核验；本机在取消限速并已有缓存后重试成功。浏览器调用直接进入插入服务，没有重新执行生图任务、自动插入 hook 或失败卡片展示流程。


## 最终修复与验收（2026-11-07）

用户要求优先保证正常功能，最终没有采用此前讨论的全局缓存键、共享默认超时或 SW 改造。

### 生效范围

`CanvasInsertionParams.imageInsertionPolicy = 'generated-result'` 是显式选项，默认关闭。接入位置是自动生成结果插入（包括失败卡片的重试）、生成图片流程助手、任务队列/对话框手动插入图片、批量生图手动插入。素材库、上传、编辑器、视频、音频等原有调用没有启用新选项。

- 仅启用选项时：原图下载最多 240 秒，单张图片插入最多 300 秒；批量外层预算按图片数计算，同时每张仍受单独 300 秒限制。
- 缓存单次读写 20 秒、Blob 解码 15 秒仍保持原值，避免把真正卡住的本地操作一律拖长。
- 将插入超时信号传到下载、缓存等待、图片加载及缓存损坏恢复；超时后停止当前可取消的加载，迟到结果不能写入画布。
- 不删除已完成缓存、不改变缓存键/元数据格式；不增加自动重新生图；CORS fetch 失败后的原有 Image 回退继续保留。
- 维持批量串行准备、整组提交、布局与去重规则。手动生成结果插入没有调用方 guard 时，捕获当前画板绑定，防止复用 Board 实例后写入另一张画板。
- 没有改生成请求、模型接口、全局 Service Worker 或数据库结构。

### 自动化验证

新增回归文件使用真实插入、缓存下载、加载与超时逻辑，模拟浏览器 I/O 和时间，保留原有 5 个默认入口对照，并添加生成结果策略的 8 个回归场景：45 秒下载、65 秒缓存批量、累计超过 60 秒的缓存步骤、CORS 回退、单张 5 分钟上限与重试、下载期间换画板、缓存读取挂起、手动插入时复用 Board 切换文档。

Hook 测试额外覆盖失败卡片的重试事件：继续使用同一结果 URL 和新策略，不调用重新生成接口，只标记一次插入成功。

### 已知边界

这是针对已确认超时路径的修复，不代表已经定位客户持续重试失败的全部原因。极慢网络、链接失效、CORS/存储限制和损坏图片仍可能失败；新策略允许等待更久，并非无限等待。下载超过 240 秒或单张准备超过 300 秒依然会终止，已终止的未完成下载在重试时可能需要重新开始。没有承诺任何网络速度下重试都会成功。

取消信号不能撤销浏览器不支持取消的已经发起的本地存储操作；相应等待有界，并保留画板写入保护。共享函数的默认策略仍为原有 30 秒下载/60 秒插入，仅显式生成结果入口获得本次修复。
